# Plan : `django-dbos` — backend DBOS pour django.tasks + cron durable

## Objectif

Package Python `django-dbos` (uv + hatchling, **layout plat**) qui intègre DBOS Transact à Django comme backend de `django.tasks` (à la django-absurd), plus un scheduler cron inspiré de django-crontask avec Sentry optionnel. API naturelle pour un dev Django : `@task`, `task.enqueue()`, `TaskResult`, `manage.py dbos_worker`, `@cron("*/5 * * * *")`.

Décisions actées : nom `django-dbos` (libre sur PyPI), Python ≥3.12 / Django ≥6.0, system DB DBOS dérivée de `settings.DATABASES` (surchargeable), périmètre V1 = tasks + cron + primitives DBOS, layout plat `django_dbos/` à la racine.

## Composants

### 1. Configuration & init DBOS
- Setting `DJANGO_DBOS = {"SYSTEM_DATABASE": ..., "NAME": ..., "APPLICATION_VERSION": "0.1.0", "QUEUES": {...}}`.
- System DB : dérivée par défaut de `DATABASES["default"]` (même serveur Postgres, base dédiée `dbos_<dbname>`), surchargeable par `DBOS_SYSTEM_DATABASE_URL` puis par le setting. SQLite possible en test rapide.
- Singleton DBOS idempotent + `DBOS.destroy()` propre pour les tests. Init au `AppConfig.ready()` ou à la demande.
- System checks : ENGINE non-postgres sans URL explicite, conflits de queues…

### 2. Backend django.tasks
- `DBOSBackend(BaseTaskBackend)` : `supports_get_result/async_task/defer/priority = True`.
- Chaque `@task` → un workflow DBOS (enregistrement paresseux, nom = chemin qualifié) exécutant le corps en `@DBOS.step()`.
- `enqueue()` → `DBOS.enqueue_workflow` sur la queue DBOS correspondante ; `run_after` → `delay_seconds` ; retour de `TaskResult` avec l'id DBOS.
- `get_result()` → mapping statuts DBOS → `TaskResultStatus` + `TaskError`.
- `takes_context=True` supporté (`attempt` = tentative du step).
- `DBOSTask` frozen dataclass, options via `@dbos_params(...)` (champ dataclass → survit à `using()`/`replace`).

### 3. Primitives DBOS (`context.py`)
- `get_dbos_context()` dans une tâche : `DBOS.sleep`, `set_event`/`get_event`, sous-workflows. Escape hatch documenté.

### 4. Worker
- `manage.py dbos_worker` : init Django → DBOS.launch() → boucle bloquante, SIGTERM/SIGINT → `DBOS.destroy()`. Flags `--queues` éventuels.

### 5. Cron (`cron.py` + `sentry.py`)
- `@cron("*/5 * * * *")` empilé sur `@task` : registre découvert via les apps installées, schedule DBOS via `create_schedule` (5 champs standard → normalisé 6 champs DBOS avec champ secondes).
- **sentry.py** (extra `django-dbos[sentry]`, no-op gracieux si sentry-sdk absent) :
  - `is_sentry_enabled()` — import guard + `sentry_sdk.get_client().is_active()`.
  - `monitor_slug(task_name)` — slug sanitisé (lowercase, `[a-z0-9_-]`, ≤50).
  - `crontab_to_monitor_config(crontab)` — `{"schedule": {"type": "crontab", "value": ...}, "timezone": ...}` ; `None` si non représentable (sub-minute) → pas de monitor.
  - `monitor_cron_task(task, crontab, sentry_monitor_config)` — wrap `task.func` avec `sentry_sdk.crons.monitor(slug, monitor_config=config)` via `dataclasses.replace` (préserve `dbos_params`) ; la config est upsertée à chaque check-in, pas de création manuelle dans l'UI Sentry.
  - Matrice : `UNSET` (défaut) = auto depuis le crontab ; `None` = désactivé ; dict custom = fourni par l'utilisateur.

### 6. Logging
- structlog configuré dans `logging.py`, binders `task_name`/`workflow_id`/`queue`/`attempt` ; helpers `capture_logs` de structlog exposés dans `django_dbos.test`. django-structlog documenté comme option utilisateur, pas une dépendance.

### 7. Outillage
- Ta config uv/ruff reprise + dependency-groups dev (ruff, commitizen, django-extensions, prek, nox, pyrefly, zizmor), test (pytest, pytest-mock, pytest-django, model-bakery, testcontainers[postgres], time-machine — pas de respx, sentry_sdk utilise urllib), doc (zensical). Extras : `sentry`. Pas de CLI dédiée : les management commands sont le CLI idiomatique Django.
- commitizen + conventional commits, CHANGELOG keepachangelog, prek, noxfile (lint, pyrefly, tests matrix, docs), CI GitHub Actions.
- Git : `git init`, branche `main`, commits conventionnels, travail par branches.

### 8. Tests
- Unitaires : mapping statuts, dérivation system DB, registre, cron (time-machine), sentry (`crontab_to_monitor_config`, `monitor_slug`, check-ins via transport Sentry en mémoire).
- Intégration testcontainers Postgres : enqueue réel, exécution worker, résultat, defer, retry après crash, cron fire.
- `django_dbos.test` : mode inline pour exécuter les tâches dans les tests.

### 9. Docs (zensical)
- Quickstart, référence API, cron + Sentry, system database, testing, migration depuis celery/crontask.
