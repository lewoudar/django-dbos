# AGENTS.md

Reference for AI coding agents (and humans) working on this repository.

## Project

`django-dbos` is a DBOS-backed backend for Django's `django.tasks` framework:
durable background tasks, cron scheduling (`@cron`), optional Sentry cron
monitors, admin pages and a worker-capacity report. Published on PyPI.

## Layout

- Flat package layout: `django_dbos/` at the repo root (no `src/`), managed by **uv** and built with **hatchling**.
- `docs/` holds the user-facing documentation (Markdown only). The zensical
  config lives at the root: `zensical.toml` (standard layout, do not move it
  into `docs/` — the docs dir resolves relative to the config file).
- Tests in `tests/` are plain functions (not Django `TestCase` unless a DB is
  needed); integration tests are marked `integration` and run against a real
  system database (PostgreSQL via testcontainers, SQLite file fallback;
  `test_cockroachdb.py` starts its own CockroachDB container).
- `examples/` holds standalone runnable projects (own `pyproject.toml`/`uv.lock`,
  `django-dbos` pulled in as an editable path dependency) demonstrating the
  package end to end; not part of the root `uv` project or its dependency
  extras, so `uv run pyrefly check` needs `--project-excludes 'examples/**'`
  (its imports are not installed in the root `.venv`) — see Commands below.

## Commands

```sh
uv run pytest                          # unit tests
uv run pytest -m integration           # integration tests (Docker recommended)
uv run coverage run -m pytest && uv run coverage combine && uv run coverage report   # coverage, see note
uv run ruff check . && uv run ruff format --check .
uv run pyrefly check --project-excludes 'examples/**'   # type check (examples/ are separate projects)
uv run deptry django_dbos              # dependency hygiene (package only)
uv run --group doc zensical build      # docs (runs from the repo root)
uv run --with playwright python scripts/admin_screenshots.py   # regenerate docs/assets/admin/*.png after admin UI changes
uv run cz bump                         # release (commitizen)
```

### Coverage

Measured with branch coverage over `django_dbos`, floor **98 %** in
`[tool.coverage.report]`. Always measure with `coverage run -m pytest`, **not**
`pytest --cov`: the pytest plugin is imported by pytest before pytest-cov
starts tracing, so module-level lines would be reported as uncovered.
Subprocesses (the plugin's pytester runs, the two-process worker) are measured
too (`parallel = true`, `patch = ["subprocess"]`): each process writes its own
`.coverage.*` file, so run `coverage combine` before `coverage report`. A
subprocess killed abruptly writes no data.

### Test environment

- `[tool.uv] exclude-newer = "7 days"` pins fresh package resolution.
- `DJANGO_SETTINGS_MODULE=tests.settings`; `filterwarnings = ["error"]` —
  warnings fail tests.
- Docker available → Postgres testcontainers for integration tests; otherwise
  SQLite file fallback.

## Publishing the docs

The Documentation workflow deploys `zensical build` to GitHub Pages. It is
skipped while the repository is private (Pages needs a paid plan there).
When the repository goes public, enable Pages **once** with the "GitHub
Actions" source — `gh api -X POST repos/lewoudar/django-dbos/pages -f build_type=workflow`
or Settings › Pages — then every push to `main` deploys.

## Conventions

- Commit messages follow **conventional commits** (commitizen,
  `cz_conventional_commits`, tag format `v$version`); CHANGELOG generated by
  commitizen through `changelog_template.md.j2` (config key
  `[tool.commitizen] template = ...`; regenerate with `cz changelog`, use
  `--incremental` to preserve manually edited sections).
- Logging through structlog under the `django_dbos` logger.
- CI workflows have their actions pinned by SHA (zizmor-checked); run
  `uv run prek run --all-files` before committing (ruff, commitizen, deptry,
  zizmor).
- The pytest plugin's runtime imports (pytest, testcontainers) are the
  `django-dbos[test]` extra; deptry checks the package against the declared
  dependencies and extras, so keep the extra in sync with the plugin.
- Python ≥ 3.12, Django ≥ 6.0.

## Process model (do not regress)

- Only `dbos worker` (and the `dbos_system` test fixture) may call
  `dbos_setup.ensure_launched()`: `DBOS.launch()` starts queue/scheduler/
  recovery threads, i.e. it turns the process into a worker. Everything else
  (backend enqueue/get_result, admin views, `capacity.collect`) goes through
  `client.get_client()` (a `DBOSClient`, system database only).
- The worker registers every known task (`tasks.known_tasks()`, filled by
  `DBOSTask.__post_init__`) as a workflow *before* launch; clients enqueue by
  workflow name and never hold workflow code.
- `manage.py migrate` migrates the system database through a `post_migrate`
  receiver (`system_db.migrate_after_django_migrate`): a plain
  `SystemDatabase` handle, never `ensure_launched()`. It must stay skipped for
  `flush` (no `plan`), non-default aliases and test databases.
- Worker heartbeats live in the `WorkerHeartbeat` model (Django database),
  not in the cache; the package ships a migration.

## Pitfalls learned the hard way

- `DBOSBackend.__init__` must not raise: Django builds the backend while
  importing task modules and running its checks. A bad queue declaration is
  stored, reported by `django_dbos.E001` and raised on enqueue. In tests,
  override the backend's `OPTIONS` with
  `tests.helpers.set_dbos_options(settings, {...})`.
- CockroachDB system database: DBOS forces `postgresql+psycopg` when given a
  URL alone, and its SQL fails on CockroachDB under psycopg 3 (typed
  parameters, `float * int`). `system_engine` builds a `cockroachdb+psycopg2`
  engine for the worker and the client (`use_listen_notify=False`), and
  `DBOS.migrate()` takes no engine, so `migrate` only creates the database:
  the worker applies DBOS' migrations on launch (`django_dbos.E005`).
- **Never patch `django.conf.settings` attributes directly** (lazy object +
  pytest-django `settings` fixture teardown = state leaks between tests).
  Patch the module's own `settings` reference instead (see
  `test_no_usable_django_database_raises` in `tests/test_settings.py`) or
  override via the `settings` fixture for plain settings.
  Overriding `DATABASES` through the fixture also raises a `UserWarning`
  (fatal with `filterwarnings = ["error"]`).
- No private SDK import (`dbos._*`): workflow functions are kept in
  `tasks_registry._workflows`, errors come from the public `dbos.error`
  alias (`from dbos import error as dbos_error` — `from dbos.error import`
  fails, it is an attribute, not a module), capacity lists active workflows
  through `DBOSClient.list_workflows`. `DBOS.get_schedule` returns a
  **dict**; the synchronous `retrieve_workflow()` refuses to run inside a
  running event loop — use the `*_async` variants in async paths.
- `django.tasks` validates task construction (module-level function, declared
  queue) at decoration time: build "rogue" tasks inside tests with
  `dataclasses.replace` after overriding `TASKS`, not at module import.
- Admin URLs must be **prepended** to the admin's URL list (`dbos_urls + urls`)
  or the admin's generic patterns swallow them; URL names are bare (`django_dbos_workflow_changelist`), the `admin:`
  namespace is added by the
  inclusion.
- DBOS/structlog log on stdout: in tests, capture a command's output with
  `call_command(..., stdout=StringIO())` rather than `capsys`.
